The live-coding playbook

These are the same six things Bondora's brief says interviewers watch for. Treat them as your operating procedure for every challenge below.

A repeatable 60-minute rhythm

MinuteDo
0–5Clarify & scope aloud. Restate the task, ask 2–3 clarifying questions, name what you'll cut if time runs short. State your data model.
5–15Skeleton. Component tree, types/interfaces, mock data or fetch stub, render the simplest possible version that shows on screen.
15–40Core requirements. Make the must-haves work end to end. Wire state, derive don't duplicate, handle loading/empty/error early.
40–50Harden. Validation, edge cases, keys, cleanup (timers/requests), a11y basics. Verify it actually runs.
50–60Polish + present. Light styling, then walk the interviewer through it: what works, trade-offs made, what you'd do next.

What earns points (the rubric)

Working functionality first

A running, presentable slice beats a half-built ambitious version. Cut scope out loud rather than freezing.

Narration & trade-offs

Explain choices as you go — why this state shape, why memoize here, what you'd change with more time.

State discipline

Single source of truth, derived state via useMemo (never duplicated into useState), immutable updates, stable keys.

Robustness

Loading / empty / error states, input validation, no console errors, cleaned-up effects (no leaks).

TypeScript fluency

Meaningful types on data and props; no any escape hatches unless justified aloud.

Presentable UI

Readable layout, sensible spacing, formatted money/percent. Doesn't need to be beautiful — needs to look finished.

Recurring traps to pre-empt: duplicating derived data into state · missing useEffect cleanup (intervals, listeners, in-flight fetches) · index-as-key on reorderable lists · stale-closure bugs in async handlers · unformatted currency · forgetting the empty state.
Challenge 1 of 6

Investment Transaction Dashboard

Archetype · Data list / dashboard ⏱ 45–55 min Derived state · useMemo · keys
Context
You're building a screen for Bondora's investor portal. Investors want to review the cash-flow on their account — interest received, principal repayments, new investments and Go & Grow top-ups/withdrawals. The backend returns a flat list of transactions; turn it into a scannable dashboard.
Build a Transactions view: a table with search, type/status filters, sortable columns and pagination, plus summary tiles that reflect the currently filtered data.

Core requirements

  1. Render transactions in a table: Date, Type, Description, Amount (colour-coded +/−), Status.
  2. A search box filtering by description (case-insensitive).
  3. A Type filter (All / Interest / Principal / Investment / Go & Grow) and a Status filter (All / Completed / Pending).
  4. Sortable by Date and Amount — click header to toggle asc/desc.
  5. Client-side pagination (10 rows/page) with prev/next and a page indicator.
  6. Three summary tiles — Total In, Total Out, Net — computed from the filtered set, not the whole list.
  7. Handle loading, empty ("no transactions match") and error states.

Provided data

A stub fetchTransactions(): Promise<Transaction[]> that resolves after ~600 ms.

type TxType   = 'interest' | 'principal' | 'investment' | 'go_grow';
type TxStatus = 'completed' | 'pending';

interface Transaction {
  id: string;
  date: string;         // ISO date
  type: TxType;
  description: string;
  amount: number;       // EUR · positive = inflow, negative = outflow
  status: TxStatus;
}

Stretch goals (if time remains)

A · Live updates. Poll a fetchLatestValue() every 10 s to refresh a "current portfolio value" tile — useEffect + setInterval with cleanup on unmount, and AbortController for the fetch. (Tests memory-leak awareness.)
B · Infinite scroll. Replace pagination with load-more using IntersectionObserver.
What's being evaluated
Derived state (never duplicate filtered/sorted into useState) · a memoised filter → sort → paginate pipeline · stable list keys · clean loading/empty/error handling.
Challenge 2 of 6

Loan Repayment Calculator

Archetype · Form → compute ⏱ 40–50 min Controlled inputs · formatting · derived array
Context
Bondora borrowers want to understand what a loan will cost before applying. Build a calculator that takes the loan parameters and shows the monthly payment and a full repayment breakdown in real time as the user adjusts the inputs.
A controlled form with live calculation of an annuity (equal-installment) loan, plus an amortization schedule table.

Core requirements

  1. Inputs: Loan amount (€500–€10,000), Term (6–60 months), Annual interest rate (%). Sliders and/or number inputs kept in sync.
  2. Live-compute and display Monthly payment, Total repayment, Total interest — recalculate on every change.
  3. Use the annuity formula (below). Handle r = 0 (interest-free) as P / n.
  4. Render the amortization schedule: per month → payment #, payment, interest portion, principal portion, remaining balance.
  5. Format money as EUR (€1,234.56) and rates as %.
  6. Validate inputs: clamp to bounds, block negatives/NaN, show inline messages; never let bad input crash the calc.
// Monthly payment (annuity):  P = principal, r = APR/12/100, n = term in months
const M = r === 0
  ? P / n
  : (P * r) / (1 - Math.pow(1 + r, -n));

Stretch goals

A · Overpayment. Add a monthly overpayment field; show how it shortens the term and cuts total interest.
B · Product presets. Toggle between two products (e.g. "Standard 12%" / "Premium 9%").
What's being evaluated
Controlled inputs kept in sync · input validation/clamping · currency & percent formatting · correctly building a derived array (schedule) · useMemo so the schedule isn't recomputed on unrelated renders · pure calc functions kept out of the component.
Challenge 3 of 6

Go & Grow Allocation Planner

Archetype · Dynamic form rows (array-in-state) ⏱ 45–55 min Immutable updates · cross-field validation
Context
Go & Grow is Bondora's simple savings-style product. An investor wants to split a monthly deposit across several named buckets (e.g. Emergency fund, House deposit, Holiday) and see each bucket's projected balance over time at the fixed Go & Grow rate.
A form with a total monthly deposit and a dynamic list of allocation rows; each row takes a share of the deposit, and the app projects growth per bucket.

Core requirements

  1. A Monthly deposit input plus a dynamic list of allocation rows — each with a name and a percentage share.
  2. Add-row and remove-row controls; rows are held as an array in state and updated immutably (no mutation).
  3. Cross-field validation: shares must sum to 100%. Show a live running total and an error when it doesn't add up; block projection while invalid.
  4. For a chosen horizon (12 / 24 / 36 months), project each bucket using the fixed Go & Grow net rate (assume 6.75% p.a., compounded monthly) and show a per-bucket balance + grand total.
  5. Sensible empty state and sensible defaults when adding a row.

Stretch goals

A · Persist. Save the plan to localStorage and restore it on load.
B · Mini bars. A tiny inline bar per bucket showing its share of the total.
What's being evaluated
Array-in-form state · immutable add / edit / remove · cross-field validation (the 100% sum rule) · derived projections kept in a pure function · sensible defaults & empty state.
Challenge 4 of 6

Async Loan Search Autocomplete

Archetype · Build-a-component / async ⏱ 45–55 min Debounce · race conditions · a11y · cleanup
Context
On Bondora's secondary market, investors search for loans by country/originator. Build a reusable autocomplete input from scratch — no combobox library — that queries as the user types and shows a keyboard-navigable dropdown.
A debounced async autocomplete with a fully accessible, keyboard-navigable suggestion list that survives out-of-order responses.

Core requirements

  1. As the user types, debounce (~300 ms) then call searchLoans(query). Don't fetch on an empty query.
  2. Show a dropdown of suggestions; click or Enter selects and fills the input.
  3. Keyboard nav: ↑/↓ move the highlight, Enter selects, Esc closes; highlighted item scrolls into view.
  4. Race conditions: if a newer request resolves before an older one, ignore the stale response (AbortController or a request-id guard).
  5. Loading indicator while fetching; "No results" empty state.
  6. Close on outside click / blur; manage focus correctly.
  7. Basic ARIA: role="combobox"/"listbox"/"option", aria-expanded, aria-activedescendant.

Provided

// Resolves after a random 200–800ms delay, so stale responses are LIKELY.
function searchLoans(q: string): Promise<{ id: string; label: string }[]>

Stretch goals

A · Cache results per query.   B · Highlight the matching substring in each suggestion.
What's being evaluated
Debounce · race-condition handling (the headline test) · focus & keyboard management · ARIA roles · effect cleanup — timers and in-flight requests cancelled on unmount, no leaks.
Challenge 5 of 6

Portfolio Watchlist Manager

Archetype · CRUD collection ⏱ 45–55 min Full state loop · immutable · persistence
Context
Investors keep a personal watchlist of holdings they're tracking. Build a manager where they can add a holding, edit it inline, remove it, and have the list persist across reloads. This is the one challenge about mutation — the full create/read/update/delete loop.
A full add / edit / remove CRUD list backed by localStorage, with an add form and inline editing.

Core requirements

  1. Add a holding via a small form: name, amount invested (€), expected annual return (%).
  2. Render holdings in a table with a computed column (projected 1-year return in €).
  3. Inline edit a row (edit-in-place with save/cancel) and remove a row (with confirm).
  4. All updates immutable; every item has a stable id.
  5. Persist to localStorage; restore on mount. Handle the empty state.
  6. A totals row: total invested and total projected return across all holdings.

Stretch goals

A · Optimistic UI. Simulate an async saveHolding() that sometimes rejects — update immediately, roll back on failure with an error message.
B · Sort by any column.
What's being evaluated
The full create/read/update/delete loop · form + list working together · immutable updates · id/key discipline · persistence & restore · (stretch) optimistic update with rollback.
Challenge 6 of 6

Loan Application Wizard

Archetype · Multi-step form / wizard ⏱ 50–60 min State across steps · per-step validation · submit lifecycle
Context
Applying for a Bondora loan is a multi-step flow — very common in fintech / KYC. Build a 3-step wizard that collects the application, validates each step, lets the user move back and forth without losing data, and submits at the end.
A guided wizard — Step 1 Loan details → Step 2 Personal / KYC → Step 3 Review & submit — with per-step validation, a progress indicator and a submit lifecycle.

Core requirements

  1. Step 1 — Loan details: amount, term, purpose (select). Step 2 — Personal: full name, email, monthly income, country. Step 3 — Review: read-only summary + Submit.
  2. Per-step validation: Next is blocked until the current step is valid; inline field errors (email format, required, numeric ranges).
  3. State is carried across steps — going Back and returning keeps entered values.
  4. A progress indicator (stepper / "Step X of 3") reflecting current position and completed steps.
  5. On submit call submitApplication(data): Promise<{ id: string }> — show loading, then a success screen with a reference id, or an error state with retry.

Stretch goals

A · Persist wizard state to sessionStorage so a mid-flow refresh doesn't lose data.   B · Deep-link steps via URL/hash.
What's being evaluated
One source of truth for form state across steps · per-step validation gating navigation · progress UI · the submit → loading → success/error lifecycle · validation logic kept separate/testable.

The other half of the interview

Verbal / open-ended question bank

AI can't help you here — these are spoken. Have a crisp answer and, where possible, a concrete story from your own work.

React internals & rendering

  • Explain the Virtual DOM and reconciliation. How does React decide what to re-render?
  • What are keys for, and what goes wrong with index-as-key? When is index-as-key actually fine?
  • What causes a component to re-render? How do React.memo, useMemo and useCallback differ and when is each worth it (and not)?
  • Functional vs class components — when would you still reach for a class (legacy codebases, error boundaries)?

Performance & memory

  • How do you prevent memory leaks in React? (effect cleanup, intervals/listeners, aborting fetches, stale closures.)
  • Lazy loading & Suspense — what problem do they solve and how do you code-split?
  • How would you diagnose and fix a slow list / janky re-render in production?

JavaScript fundamentals

  • Promises vs async/await; how do you run things in parallel vs sequence; error handling.
  • Event delegation — what is it, why use it, how does bubbling make it work?
  • DOM behaviour: event loop, microtasks vs macrotasks, why a setTimeout(…, 0) runs after a resolved promise.

State management & architecture

  • Local vs global state — how do you decide? When does Context API bite you (re-render fan-out)?
  • Redux vs Zustand vs Context — trade-offs and when you'd pick each.
  • CSS/styling approaches in React (CSS Modules, CSS-in-JS, Tailwind, plain CSS) — pros/cons and your preference.
  • Compare React with another framework you've used and when you'd choose each.

Experience & fit (have a story ready)

  • A technical decision you made, the trade-offs, and how it turned out.
  • A difficult front-end problem you solved and a performance improvement you drove (with rough numbers).
  • Your openness to legacy work — plain JS / jQuery, CMS-related work, and small back-end changes in .NET / Java / PHP. (Bondora asks this directly; answer honestly and positively.)
